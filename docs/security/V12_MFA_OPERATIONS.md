# V12 native MFA and scoped operation proofs

Native identities use their existing JWT/refresh authority, not a second login system. Verified active users and verified pending staff applicants can enroll an individual authenticator after password reauthentication. Pending applicants cannot issue administrative proofs. Institutional and unknown-source sessions cannot select a native account by matching an ID.

Configure `MFA_ENCRYPTION_KEY` through the private runtime secret store: exactly 32 cryptographically random bytes encoded as canonical unpadded base64url. No configured key means MFA enrollment and privileged proof operations return dependency unavailable. Do not paste this key into Git, logs, screenshots or support tickets. Preserve the encryption key securely: changing it without a factor migration makes existing encrypted factors unreadable. Password-only replacement of a confirmed factor is denied; operator recovery requires a separately audited recovery procedure and is not exposed here.

Factor setup expires after ten minutes. TOTP uses RFC 6238 HMAC-SHA1, six digits and a 30-second interval with one adjacent interval allowed on each side. A persisted atomic timestep comparison prevents replay across API processes. Secrets use AES-256-GCM with unique random IVs and account/factor identifiers as authenticated associated data. Enrollment material is returned only to its authenticated owner with `Cache-Control: no-store`; summaries and logs never return it.

A five-minute step-up proof is random, stored only as a SHA-256 hash and bound to actor ID, current authority revision, action, resource, operation ID and the SHA-256 digest of the canonical command. Consuming services must independently derive that digest, check live role/capability/tenant/resource scope and commit the command idempotently using compare-and-set. Exact command retries are permitted while the proof is current; altered commands cannot reuse it. This proof alone does not grant a role or an event assignment.

Mongo collections: `platform_mfa_factors` is keyed by native user ID; `platform_mfa_proofs` is keyed by proof hash and has an expiry TTL index. Proof expiry is enforced in code immediately, regardless of TTL cleanup timing. Pending-factor replacement and all confirmation/timestep/proof updates use compare-and-set; malformed authority or time metadata fails closed. No existing account is auto-enrolled and no production owner or credential is fabricated.

Authenticated endpoints: GET `/auth/mfa/status`; POST `/auth/mfa/enrollment`, `/confirmation`, `/step-up`. Credential JSON is bounded to 4 KiB before decoding. Each account/operation has five attempts per five minutes independent of source address; an additional address counter limits account cycling. These in-process abuse counters need a shared gateway limiter for multi-replica deployments; replay prevention remains persisted in Mongo across replicas.

Automated tests exercise published TOTP vectors, encryption binding, native session authority, expiry, invalid requests, denied pending/participant privileges and concurrent independent Mongo repositories. This proves the software flow, not production MFA activation, production operator identity, email ownership or human acceptance. TOTP is not phishing-resistant. Production bootstrap and administrative approval consume these controls in subsequent V12 deliveries.
