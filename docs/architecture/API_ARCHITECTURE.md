# API architecture

Ktor 3, JVM, MongoDB. The API is the only component allowed to hold
institutional credentials, so it is also the only component that has to be
defended.

## Endpoints

The API currently exposes operational endpoints only. No product endpoint
exists yet.

| Method | Path | Success | Purpose |
|---|---|---|---|
| GET | `/health` | 200 | Liveness plus dependency state, for humans and dashboards |
| GET | `/ready` | 200 / 503 | Readiness, for load balancers |
| GET | `/version` | 200 | Build identification |

### `GET /health`

Always answers 200 while the process is alive. The HTTP status answers "can
this process serve a request at all"; the body answers "is everything it
depends on healthy".

```json
{
  "service": "companero-api",
  "status": "up",
  "version": "0.0.0-dev",
  "environment": "local",
  "timestamp": "2026-09-30T05:26:38.385Z",
  "dependencies": [
    { "name": "mongodb", "status": "degraded", "detail": "not_configured" }
  ]
}
```

Aggregation rule: a dependency that is unreachable produces overall
`degraded`, not `down`. A process that cannot reach its database is still a
running process, and reporting it as `down` would make `/health` useless for
distinguishing "crashed" from "degraded".

### `GET /ready`

`200` only when every dependency is `up`. Otherwise `503` with status `down`.

**`/ready` returning 503 while no database is configured is correct
behaviour, not a failure.** It is the signal a load balancer needs to keep
traffic away from an instance that cannot serve it. A fresh clone boots with
no infrastructure and reports itself honestly rather than claiming to be
ready.

### `GET /version`

Never touches the database, so it stays answerable while Mongo is down. Used
to confirm which build is running.

## Error contract

All errors use the shared envelope, so the Android client parses one shape.

```json
{
  "success": false,
  "error": {
    "code": "not_found",
    "message": "Resource not found",
    "fieldErrors": [],
    "requestId": "3f1c..."
  }
}
```

`ApiErrorCode` is a closed enum. `StatusPages` maps exceptions to it, so an
unmapped exception becomes a generic `internal_error` with a `requestId`
instead of a stack trace reaching the client.

`requestId` is generated by the CallId plugin, echoed in the `X-Request-Id`
header, and attached to the error body and to logs. It is the only handle a
user can quote when reporting a problem.

## Configuration

`SettingsLoader` reads plain environment variables. There is no YAML and no
secrets file, because a file on disk is one more thing to rotate and one more
way to leak.

| Variable | Required | Rule |
|---|---|---|
| `APP_ENV` | yes | `local`, `development`, `staging`, `production` |
| `MONGODB_DATABASE` | yes | Non-blank |
| `MONGODB_URI` | no | Blank is legal: boot without a database |
| `JWT_SECRET` | production only | Minimum 32 characters |
| `API_HOST`, `API_PORT` | no | Defaults `127.0.0.1`, `8080` |

Failure behaviour is deliberate:

- **Boot fails loudly, naming the variable, never its value.** A wrong
  connection string does not print the string.
- `JWT_SECRET` is optional locally so a new contributor needs no setup, and
  **mandatory in production** so a deploy cannot quietly run unauthenticated.
- Invalid values produce `ConfigurationException` before the server binds,
  never a 500 on the first request.

## Persistence

`MongoConnection` hides the driver behind an interface and exposes its
lifecycle explicitly rather than through a lazily self-referencing holder,
which would have been a recursion bug waiting to happen.

No repository or collection exists yet. The database is wired and health-checked
but stores nothing; attendance persistence is future work. That is why the
service is honest about a missing database rather than defaulting to one.

## Mock providers are locked out of production

`ProviderRegistry.requireEnvironmentSatisfied` is called from
`Application.module`, before plugins are installed. `staging` and `production`
throw if any provider is a mock.

This check is in the boot path, not in a test. See the bug register: it existed
as a function and was not called, which is exactly the failure mode a unit
test cannot catch.

## Plugins

| Plugin | Purpose |
|---|---|
| ContentNegotiation | kotlinx.serialization, shared `Json` config |
| CallId | `X-Request-Id` generation and propagation |
| CallLogging | Method, path, status, duration, request id |
| CORS | Restricted origins; no wildcard in production |
| StatusPages | Exceptions to the shared `ApiError` envelope |

Logging is Logback with a JSON-free, human-readable pattern. The value at risk
is a student's schedule, so access logging is on and body logging is off.
